## Goal

autoware-drift sits in AutoSDV as a submodule without changing anyone's build; its
full-size results are frozen as a regression gate before anything in it changes; and the
question that sets every later scale constant is answered: does the planner fit on a
Jetson AGX Orin next to the rest of the stack?

## Tasks

### 1.1 Submodule

- `src/planning/external/autoware-drift`, `url = https://github.com/jerry73204/autoware-drift.git`,
  `branch = main` in `.gitmodules` (our fork convention).
- `race_planner` keeps its `COLCON_IGNORE`. `drift_controller` and `drift_launch` build as
  they are (pure Python, no new dependencies); confirm they do not collide with any
  AutoSDV package or topic name.
- A setup step in `setup/autosdv_setup/registry.py` for the planner's Python dependencies
  (CasADi with IPOPT, HPIPM) and acados, in no default profile: selected by hand until
  phase 6 makes it a vehicle step.

**Check:** a clean `just build` and `just test` on amd64 and on an Orin, with and without
the step's dependencies installed, give the same package list and results as before the
submodule, plus the two autoware-drift packages.

### 1.2 Regression gate (in autoware-drift)

- A `just regress` recipe in autoware-drift that runs a fixed set with `RP_DET=1`: the
  race_planner test suite, and closed-loop runs of the M4 harness
  (`studies/mode_choice_m4.py`) on its courses, and records each run's outputs as hashes in
  a committed file.
- `just regress check` re-runs the set and fails on any difference. The rule, written in
  autoware-drift's README: run it before every push to `main`.
- The gate needs `$SWB` (tests and the sim plant read swb's specs and courses); the recipe
  says so and stops if it is unset, rather than skipping runs silently.

**Check:** the gate passes twice in a row on an unchanged tree, and fails when one
constant (for example `axle.py`'s `SMOOTH`) is changed on a scratch branch.

### 1.3 Orin benchmark

Planner, headless, on its own plant (`sim.Plant`), with a provisional small-car spec
(car A's twin spec with `drive_axle: rear`, locked differential assumed, mass 5 kg), on a
lap of a COSS-sized course (a scaled swb course is enough before phase 3).

Load, in the order the spec's fallbacks need:
1. AutoSDV's stack on the Orin as a race would run it: cuda_ndt localization and the
   vehicle stack replaying a COSS bag (`just sim logging` with `pose_source:=cuda_ndt`),
   perception on;
2. the same with perception off;
3. as 1, plus three replayed image streams through rig_localization, if it builds on the
   Orin by then (otherwise recorded as not measured, and repeated in phase 5).

Measure per configuration: L1 solve time (p50, p95, max) and how many re-plans miss the
1 s budget, at horizons from autoware-drift's default down to the Froude-scaled one; L2
tick time at 50 Hz; CPU and GPU load (`scripts/profiling/jetson_gpu_sampler.py`,
`scripts/profiling/kernel_cpu_report.sh`).

A first acados NMPC: the tracker's model (`tracker.py`) generated by acados' Python front
end, solved from C on the Orin on recorded states; solve time p50/p95/max at 50 Hz.

**Check:** a report, `docs/reports/race-stack-orin-benchmark.md`, with the tables above and
a decision: horizon and re-plan period for the small-car profile, and whether perception
must be off in a race. If nothing fits, the phase ends with that finding and the spec's
fallback order (perception off, then a longer re-plan period and shorter horizon) is
taken up before phase 3.
